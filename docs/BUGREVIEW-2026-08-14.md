# Bug review of 2026-08-14 — findings and resolutions

An adversarially verified bug review was run against commit `3485501`
(the UI re-review fixes). Method: parallel finders across the engine,
scoring, live path, importers, audio I/O, CLI and configuration; every
finding was then attacked by two independent verifiers with opposing
lenses — one trying to construct the failure, one hunting for an existing
guard, both instructed to refute when uncertain — and only findings
neither could knock down were kept. 53 raised, 27 refuted, 7 contested,
19 confirmed; 17 unique after dedupe. Two more of the same class were
found while fixing and are included.

This document is the permanent record. IDs group by theme: **W** = the
wait-mode wiring, **N** = non-finite floats reaching the audio path,
**P** = scoring correctness, **M**/**G**/**D** = the MusicXML, Guitar Pro
and MIDI importers, **C** = contested findings that needed investigation
before a verdict.

The prior audit is `AUDIT-2026-08-13.md`; this review covers what that
one did not reach.

## W — the wait-mode wiring (all fixed)

Wait mode halts playback until the player plays the note on screen. Its
failure mode is the worst one this project has: playback stops and never
restarts, and the note the player did play is scored a miss.

| ID | Where | Finding | Resolution |
|----|-------|---------|------------|
| W1 | `cmd/guitartutor/live.go` `newOnNotes` | The gate armed from two separate reads — `WaitingOn()` under the engine mutex, then `WaitGeneration()` lock-free. Between them the render thread can release one wait and engage the next, so the gate armed with the PREVIOUS wait's events under the NEW generation: it could never be satisfied (those notes are behind the playhead) and never re-armed (the generation already matched). Playback froze permanently and the note the player did play scored a miss. A reviewer reproduced it deterministically: after 200 batches of the correct key 40, the engine was still waiting at generation 3 armed on key 43. | `Engine.WaitingOn` now returns the events, the generation they belong to, and the waiting flag from one locked snapshot, so the pair cannot be mismatched by construction. Tests: `TestWaitingOnCarriesItsOwnGeneration`, `TestWaitingOnSnapshotIsSingleValued` (concurrent, run under `-race`). |
| W1b | `internal/integration/wait_live_test.go` | The end-to-end wait test hand-copied the buggy two-read wiring, which is why it could not catch W1 — the test and the code were wrong in the same way. | Rewired through the new single call, with a comment saying to keep it a faithful copy and why the shared API now makes that structural rather than a matter of vigilance. |
| W2 | `internal/engine/wait.go` `waitPointAt` | Waits engaged on *any* `RoleUser` track's note, but only ONE track is scored and drawn. A piece with two user parts — which the text format allows and duet `.gtab` files use — halted at a note the view never draws and the scorer was never told to expect, so nothing could release it. | New `Engine.SetWaitTrack` narrows waits to the practiced track; the default (every user track) is unchanged for callers with no single part. Arming, the event list, and consuming the release all route through one `waitsOn` predicate so they cannot disagree. Tests: `TestWaitTrackRestrictsWaitsToOneTrack`, `TestWaitTrackDefaultWaitsOnEveryUserTrack`, `TestWaitTrackOutOfRangeFallsBackToEveryUserTrack`. |
| W3 | `cmd/guitartutor/main.go` `-track` | The flag was documented as display-only but also chose the scored track, while wait mode still keyed off `RoleUser` — so `-track n` pointing at a backing part produced a wait nothing could release. Three things had to agree about which track was being practiced and each was told separately. | `ui.New` sets the engine's wait track to the track it displays, and `setupListen` reads the scored track from the view (`App.Track()`) instead of taking it as a parameter — one source of truth, so display, scoring and waiting cannot name different music. The flag's help text now says what it actually does. Test: `TestNewNarrowsWaitModeToTheDisplayedTrack`. |

## N — non-finite floats reaching the audio path (all fixed)

Go's float comparisons are all false for NaN, so every guard written as
`if x < lo || x > hi` is blind to it. `int(NaN)` is `MinInt64`. Together
those two facts account for this whole group.

| ID | Where | Finding | Resolution |
|----|-------|---------|------------|
| N1 | `internal/engine/backing.go` `mixBacking` | `if p < 0 \|\| p > last` does not reject NaN, so `j := int(p)` became `MinInt64` and the next line indexed the backing buffer out of range — a panic **on the realtime audio thread**. Reproduced with `render -backing-offset NaN`. | Guard rewritten as `!(p >= 0 && p <= last)`, which rejects NaN and both infinities and is otherwise identical; the gain early-out had the same blindness and got the same treatment. `SetBackingTrack` now refuses a non-finite offset at the boundary too, so the realtime path is not the last line of defence. Tests: `TestMixBackingNonFinitePositionSilent`, `TestBackingNonFiniteOffsetRefused`. |
| N2 | `internal/engine/backing.go` `SetBackingGain` | NaN passed the `g < 0` clamp and the `== 0` early-out, so every backing sample became NaN, the whole mix with it, and quantization wrote it as full-scale −32768: **eight seconds of maximum-amplitude noise**, exit status 0. Reproduced with `render -backing-gain NaN` — 98.8% of samples at the negative rail. | Non-finite gains are refused. Test: `TestBackingNonFiniteGainRefused`. |
| N3 | `internal/wavio/wavio.go` `quantize` | `int(math.Round(x))` is `MinInt64` for NaN and +Inf, so the positive saturation branch never fired and the negative one did: a positive over-range sample saturated to full-scale NEGATIVE and NaN became −32768 instead of silence. This also hit finite input — `quantize(1e30)` returned −32768. | Saturation now happens in float space before any int conversion; NaN maps to 0, each infinity to its own rail. Total: every `float64` maps to a defined `int16`. Tests: `TestQuantizeNonFinite`, `TestWriteNonFiniteSamples`. |
| N4 | `internal/engine/render.go` `setScale` | Found while fixing N1. The same blind clamp: `SetTempoScale(NaN)` stored NaN, poisoning frames-per-tick, the segment end, the published BPM, and the backing position — which is how a NaN could still reach `mixBacking` with both backing setters fixed. | Non-finite scales are refused; there is no sensible clamp for "not a number". Test: `TestSetTempoScaleRefusesNonFinite`. |
| N5 | `internal/audiofile/audiofile.go` `Load` | Found while fixing N3. A 32-bit-float WAV can carry NaN or ±Inf as valid bit patterns — not a decode error, so nothing rejected them. N3 makes the offline render merely silent, but the live path writes `float32` straight to the device, so those samples reached the player's headphones as a rail. | Non-finite samples are silenced before resampling (which would otherwise smear them across neighbours), with a warning naming the count. Test: `TestLoadSilencesNonFiniteSamples`. |

## P — scoring correctness (all fixed)

Judged against the project's stated worst failure mode: a false "you
missed".

| ID | Where | Finding | Resolution |
|----|-------|---------|------------|
| P1 | `internal/practice` `DetectedStrum` | The chord-group chooser picked the LARGEST group in the window regardless of how far away it was, so with 16th-note stabs at 120 BPM a strum answering a 5-note Am finalized the 6-note C/G a beat later — deleting expectations the player had not reached, scoring them against audio that was not theirs, and leaving the chord they did play to age into misses. | Proximity is now primary, with a `chordProximityMillis = 50` slop inside which size breaks the tie. 50 ms is the onset detector's own placement budget and is far below any notated rhythm the app scores (16ths at 120 BPM are 125 ms apart), so two chord ticks closer than that are a rolled chord, not two beats. Chosen in two passes rather than one best-so-far scan, because "nearer unless comparably near, then larger" is not transitive and a single scan would depend on candidate order. Tests: `TestScorerStrumBelongsToTheChordItLandedOn` (the exact reported scenario — pre-fix it produced six results at the wrong tick, two of them hard misses), `TestScorerStrumSizeBreaksProximityTies` guarding the mirror bug. |
| P2 | `internal/pitch` `Note`, `internal/practice` | A legato slide is tracked as ONE note keeping the ORIGIN key, while the score emits the destination as a separate event with the DESTINATION key — so every slide in a piece was an expectation that could not be matched however well it was played. `Note.Cents` being a median over the whole note meant the trajectory was averaged away entirely. | The tracker keeps its one-note contract (splitting it would risk manufacturing a phantom detection at the destination — the false-hit-then-false-miss pattern P1 is about, and heavy vibrato would fragment). Instead `Note` gains `MinCents`/`MaxCents`/`EndCents` from the already-median-filtered per-hop deviations, and the scorer matches `TechSlide` expectations against that trajectory after ordinary matching: Hit when the pitch settled at the key, Close when it only swept through. This is the one place the one-detection-one-expectation rule is deliberately broken — a legato slide is one sounded string answering two written notes. Tests: `TestScorerSlideDestinationIsMatchable`, `TestScorerSlideChainCreditsEveryStep`, `TestScorerSlideCreditIsNarrow` (four cases that must stay misses), `TestTrackerReportsTrajectory`. |
| P3 | `internal/practice` `WaitGate`, `cmd/guitartutor/live.go` | A wait point on a dead (muted) note could never be satisfied: the gate needed a pitched detection, and a damped string produces no trackable f0. Playback halted at the first `x` in a piece and never resumed. | `WaitGate.OfferStrum` accepts a fresh attack as evidence for dead events — deliberately without `deadlineResult`'s chroma-prominence test, since at a frozen wait point exactly one thing is being asked for and demanding pitch-class energy from a pitchless note risks the one outcome worse than a wrong verdict. `WaitConfirmed` records a Close for it rather than letting it age against machinery latency. **The wiring in `cmd` had to change too**, or the fix was inert: `OnStrums` fed only the scorer, so `newOnNotes` became a `liveWiring` struct whose two callbacks share the arming state, and strums arriving in the same batch that arms the gate are re-offered once so an anticipating player's attack is not silently dropped. Tests: `TestWaitGateDeadNoteReleasedByStrum`, `TestWaitGateDeadNoteInChord`, `TestScorerWaitConfirmedDeadNote`, plus end-to-end `TestDeadNoteWaitReleasedByStrum` and `TestDeadNoteWaitStrumInTheArmingBatch` in `cmd` (both verified to fail without the wiring change). |
| C1 | `internal/practice` `WaitGate` | **Contested, confirmed — but not for the reason claimed.** The stale-attack window is load-dependent: a note ringing from the previous wait point releases the next same-key one when `lag + gap <= 7200` frames. At 16ths/120 BPM that usually fails, but at 32nds/120 or 16ths/160 it holds comfortably — so it is real, and no value of `waitArmGraceFrames` closes it at every tempo. | Fixed structurally rather than by tuning: the gate now tracks attack identity, promoting credited attacks to a `spent` set on re-arm and pruning entries older than the new floor. One attack, one wait point, tempo-independent. The credited/spent split preserves the earlier deliberate leniency that lets one detection credit both halves of a unison chord within a single arm. `waitArmGraceFrames` stays at 150 ms. Tests: `TestWaitGateSpentAttackCannotRelease`, `TestWaitGateSpentSetForgetsStaleAttacks`. `TestWaitGateRearmResets` was inverted — it re-offered a literally identical detection and asserted release, encoding the bug. |
| C2 | `internal/practice` `Detected` | **Contested, confirmed.** The oldest-deadline-wins rule did not exclude abandoned expectations, so one marked to produce no verdict could outrank a live one and steal its detection — turning a silent drop plus a Hit into a Hit plus a false Miss. | Match tiers with live-ness outranking exactness. An exact-key abandoned expectation beating an octave-off live one yields one Hit and one false Miss; the other order yields one Close and no Miss — same accuracy, one fewer false "you missed". Abandoned expectations stay matchable, last. Test: `TestScorerLiveExpectationOutranksAbandoned`. |

## M — the MusicXML importer (all fixed)

| ID | Where | Finding | Resolution |
|----|-------|---------|------------|
| M1 | `internal/mxlimport` `parse.go` | `<attributes><transpose>` was never read, so the importer treated written pitch as sounding pitch. A guitar part notated in treble clef with `<octave-change>-1</octave-change>` — the near-universal convention, emitted by MuseScore, Guitar Pro and Finale — imported **an octave sharp throughout**, with every fret position and every scoring expectation wrong and no warning. With authored `<technical>` present the derived pitch came out right but the importer disagreed with itself on all 16 fixture notes, which was the only visible tell. | Chromatic + 12×octave-change applied to sounding pitch, honouring `<double/>` and per-staff `<transpose number=>` so a transposed staff 2 cannot leak onto staff 1. `<diatonic>` is deliberately ignored — it is a respelling hint that never moves sounding pitch. Tests: `TestTransposeAppliedToSoundingPitch` (4 cases) and, strongest, `TestTransposedFixtureMatchesCanonical` — a transposed copy of the shared fixture must import to the same score as the canonical one. |
| M2 | `internal/mxlimport` `finish` | A `<chord>` mixing authored and unfingered notes **silently lost a note**. `fretting.Assign` was handed only the unfingered notes with no knowledge of which strings the authored ones held; it picked a string an authored note already occupied, the same-string truncation pass set the earlier note's `end = start`, and the zero-length filter dropped it. The only warning said "truncated 1 note(s)" — the drop itself was silent, so the player was shown an incomplete chord and then scored on it. | Authored strings are claimed per onset and the unfingered notes go through the *same* `fretting.Assign` restricted to a sub-tuning of the free strings — the mixed case now uses the machinery the all-unfingered case uses, not a second placement rule. A note that still finds nowhere warns by key and tick, and any note left zero-length by a same-tick same-string attack is reported rather than vanishing. Tests: `TestMixedChordKeepsEveryNote`, `TestMixedChordUnplaceableNoteWarns`. |
| M3 | `internal/mxlimport` | `<measure implicit="yes">` (a pickup/anacrusis) was never read, so its notes were laid out from the start of a full bar and every note in the piece sat wrong relative to the barlines — the metronome and the music disagreed. | The score model has no short bar, so the bar stays full and the pickup's content is right-aligned to end exactly where beat 1 of bar 1 begins, carrying its tempo marks with it. The underfull-measure warning is suppressed for pickups (being underfull is their definition) and replaced by a coalesced one. Tests: `TestPickupMeasureRightAligned`, `TestPickupMeasureTempoShifted`. |
| M4 | `internal/mxlimport` tie table | Ties were tracked in a map keyed by pitch alone, so a unison — the same pitch on two different strings, extremely common in guitar music — collided: one tie start overwrote the other, one chain never resolved, and its note's duration was wrong. | Keyed by string and `<tie number>` as well as pitch, with agreement required where both ends state one and a more-specific match winning, so files that author the string on only one end still resolve as before. The map became a scan, so it is bounded: dead ties pruned per measure plus a `maxOpenTies = 1024` cap with a warning — unbounded it would have had the same quadratic shape as the earlier audit's E2. Tests: `TestTiedUnisonKeepsBothChains`, `TestTieNumberDistinguishesChains`. |
| M5 | `internal/mxlimport` | `<unpitched>` warned once **per note**, so importing a drum staff buried every warning that mattered under hundreds of identical lines. | Coalesced to one aggregate per part, following the counter pattern the file already established; the other per-note floods in the same loop were coalesced too. Test: `TestUnpitchedNotesWarnOnce`. |
| X1 | `internal/mxlimport` `repeat.go` (new) | **Contested — resolved as an undocumented bug, not a known limitation.** README claims MusicXML import with no caveat; ROADMAP enumerates the supported subset and mentions repeats neither way; the package's own "subset boundaries, stated plainly" list omitted them; and a grep for repeat/volta/segno/coda found zero handling anywhere. So a piece whose form is "AABA via repeat signs" imported as "ABA" — a third of the music missing — with nothing to say so. That is exactly the silent data loss the rest of the package refuses to commit. | Forward/backward repeats and voltas are expanded into a flat play order, computed once from the union of every part's barlines and applied to all parts (parts share barlines in MusicXML, and expanding per-part would desynchronise them). D.C./D.S./coda/fine are **not** expanded — their semantics compose in ways no bounded reading settles, and a wrong expansion is worse than none — so they warn instead. Malformed markup (unreadable volta number, a volta that never closes) keeps the written order and warns. Bounded by `maxPlanMeasures`; the walk provably advances every iteration. Tests: `TestBackwardRepeatExpanded`, `TestVoltaEndingsExpanded`, `TestRepeatTimesHonoured`, `TestJumpDirectionsWarn`, `TestUnbalancedVoltaNotExpanded`, `TestNoRepeatMarkupIsSilent`. |
| X1b | `internal/mxlimport` `parse.go` | Found *because* of X1: state that persists across measures — divisions, meter, transposition, pending meter — was mutated as the walk proceeded, so a meter change inside a repeated section leaked into pass 2 and the bar layout and the notes parted company. | Snapshotted per measure and restored on revisit, with meter entries re-emitted whenever the effective meter at a measure start disagrees with the map. Test: `TestRepeatRestoresMeterAcrossPasses`. |

Consumer-visible changes from M1/M3/X1: a file with repeats now produces
more bars and events than it has measures (the piece is genuinely
longer); a pickup file's notated bar 1 is score bar 2; and transposing
parts import at a different — correct — pitch than before. No structural
change to the score model, and the result still passes `score.Validate`.

## G / D — the Guitar Pro and MIDI importers (all fixed)

Importers decide what the player is told to play and what their playing
is scored against, so a silent import error means the app confidently
teaches the wrong notes.

| ID | Where | Finding | Resolution |
|----|-------|---------|------------|
| G1 | `internal/gpimport` `beatNotes`, `trackOrder` | Guitar Pro drum notes carry `Element`/`Variation` properties, never `String`/`Fret`, so every hit took the "no String/Fret properties; skipped" branch — one warning **per note** — and the whole track became rests. Worse, roles were assigned by position in the kept slice, so a drums-first file handed the player an empty practice part with no explanation. | New `gpTrack.percussion()` detects a kit from any of the three markers GPIF uses across versions (`InstrumentSet` type/name, `Instrument ref="drmkt"`, General MIDI primary channel 9). Percussion tracks are dropped before role assignment with one warning naming the track, matching midiimport's existing precedent. An all-percussion file now errors with "every track in the file is percussion" rather than a score of silence. Tests: `TestPercussionTrackSkipped`, `TestPercussionMarkers` (table, with negative controls), `TestAllPercussionTracksError`. |
| G2 | `internal/gpimport` `barBeats` | `<MasterBar><Bars>` is indexed by the *resolved* track order, but `barBeats` subscripted it with the track's index in the *filtered* slice. One dropped track and every later track was shown — and scored against — a different instrument's music. G1 makes dropping more likely, so the two compound. | `trackRef` carries the original slot alongside the track; `trackOrder` keeps a placeholder for each filtered slot; the parameter is renamed `ti` → `orig` throughout so the meaning cannot be reintroduced by accident, and warnings now quote the file's own track number. Tests: `TestFilteredTrackKeepsItsOwnBars`, `TestPercussionFilterKeepsLaterTrackBars`. |
| G3 | `internal/gpimport` `rhythmDur` | Found during the sweep. The tuplet computation `dur * int64(den)` was unbounded; a hostile denominator wrapped int64, and `fillBar` then truncated the result and blamed "overfill" — the note was wrong with nothing naming the real cause. | Bounded by `maxTupletPart = 64` with its own warning. Test: `TestHostileTuplet`. |
| D1 | `internal/midiimport` `readTrack` | **Partly refuted, partly real.** The channel-10 percussion half was already correct — the filter, the warning, the package doc and `TestImportPercussionSkipped` all already existed and agreed. What was real: nothing separated *melodic* channels, so a type-0 file (all instruments on one track, separated only by channel — and gomidi does not auto-split on read) merged the whole band into one unplayable part, and `Track.Program` took the first program change on *any* channel, labelling that merged part with whichever instrument spoke first. | Split into one part per channel, keyed on **channels actually used** rather than the format byte: type-1 tracks are near-always single-channel so it is a no-op for them, a multi-channel type-1 track is genuinely multi-instrument for the same reason, and format bytes are widely mis-written. Programs are now tracked per channel. Tests: `TestImportType0SplitsByChannel` (real type-0 fixture, format byte patched and read back), `TestImportMultiChannelTrackSplit`, `TestImportPerChannelProgram`, and the guard `TestImportSingleChannelNotSplit`. |

Result-shape note for D1/G1: `Import` and `ImportFile` signatures are
unchanged and no caller needed editing, but a multi-channel MIDI now
yields more tracks than the file has (named `"<name> (channel N)"`), so
`-track` numbering shifts for those files, and a `.gp`'s percussion
tracks no longer appear at all. Verified against `testdata/fixture_riff.mid`:
still exactly one track, no warnings — the split really is inert for the
ordinary case.

## V — regressions in the fixes themselves (found by the verification pass, all fixed)

The fixes above were then attacked the same way the original findings
were: independent reviewers per changed area, each finding put to two
opposing-lens verifiers, several of which reproduced the failure with a
throwaway test rather than arguing it. Twelve defects survived, every one
of them introduced by this round's own work.

That is the headline result of this document. Nine of the twenty-three
original findings concerned wait mode and scoring, and the fixes for them
interacted: attack identity (C1) against slide matching (P2) produced a
new permanent freeze (V3); the strum path added for dead notes (P3) let
any later strum skip a wait point (V1/V2); tightening one bound to fix
that opened a false-miss on slides (V6). The rule the whole cluster
illustrates is that a fix to the "never falsely say you missed"
machinery is itself the most likely source of the next false miss, and
nothing but an adversarial second pass finds them.

| ID | Where | Finding | Resolution |
|----|-------|---------|------------|
| V1 | `cmd/guitartutor/live.go` `onStrums` | **Introduced by the P3 fix.** The wait gate stays satisfied from the moment it fills until something re-arms it, and only `onNotes` arms. `onStrums` consulted nothing else, so every strum arriving after a confirmation found a full gate and released whatever wait came next: the player strummed once and the piece ran on through wait points they never answered. Wait mode silently stopped waiting — worse than the halt the strum path was added to cure. | `armedLive()` gates the strum path on the engine actually being halted on the wait the gate is armed for, read from one `WaitingOn` snapshot for the same reason the arming path is. Tests: `TestStaleGateCannotReleaseTheNextWait`, `TestStrumsAreInertWhileNothingIsWaiting` (both verified to fail without the guard). |
| V2 | `internal/practice` `WaitGate.Offer`/`OfferStrum` | The same defect one level down: the gate answered "satisfied" to every caller that asked after it filled. V1 fixed the caller; leaving the gate as it was would leave the trap set for the next one. | New `satisfied()` reports completion **once per arm**, reset by `Arm`. `TestWaitGateChordAcrossOffers` had explicitly pinned the old behaviour ("once satisfied it stays satisfied") — that assertion was inverted, with a comment recording that it encoded the bug. |
| V3 | `internal/practice` `WaitGate.Offer` | **A collision between two fixes made in the same round.** Attack identity (C1) says one attack cannot release two wait points; slide matching (P2) says a slide destination is evidenced by the origin note's trajectory. But a legato slide has no attack of its own — the origin's, already spent releasing the origin's wait point, is the only evidence there will ever be. So a wait point on a slide destination could never be released: playback halted at every slide in the piece, permanently. | Slide destinations are exempt from the spent check; ordinary notes are not. Tests: `TestWaitGateSlideDestinationAcceptsTheSpentOriginAttack` and, guarding the other side, `TestWaitGateSpentAttackStillBarredFromAPitchedWait`. |
| V4 | `internal/practice` `slideVerdict`, `reachedKey` | **Introduced by the P2 fix.** A note left ringing sits at its own pitch and never moves, so its trajectory trivially "reached" any later slide expectation *at that same pitch*. One played note was credited twice — once by ordinary matching, once as a slide the player never performed. | A legato slide is tracked as one note keeping the ORIGIN key, so a genuine slide destination is never the detection's own key; equal keys mean the note did not move. Test: `TestScorerSlideNotCreditedByASustainedNote`. |
| V5 | `internal/practice` slide tolerances | The V3 exemption then went too far the other way. Reach was measured against `CloseCents` (70 — most of a semitone), so a note merely held with ordinary vibrato "reached" a key a fret away: it released slide wait points the player never slid to, and on the scoring side one sustained note collected credit for four separate slide destinations. | Two different questions, two different bounds. The **gate** now asks whether the destination is what the string is sounding NOW (`settledAt`, using the tight full-credit bound) — releasing a halt requires the player to be holding the note, since the position is frozen. The **scorer** keeps the swept-range test for partial credit, but at the tight bound too. Tests: `TestWaitGateSlideReachIsTight` (six cases, including a bend held at the destination, which is deliberately accepted). |
| V6 | `internal/practice` `WaitConfirmed`, `cmd/guitartutor/live.go` | A correctly played slide **at a wait point** still scored a Miss. `WaitConfirmed` pre-matches by key and a slide's detection carries the ORIGIN key, so nothing matched; and the wiring's `confirmBuf` keeps only FRESH attacks, which a legato slide by definition is not — so it handed `WaitConfirmed` an empty list. The player slid correctly, playback resumed, and the note was marked missed: the worst failure mode, reached through the fix meant to prevent it. | `WaitConfirmed` grades a slide destination off the trajectory, and `practice.ConfirmsSlide` lets the wiring keep the one detection that proves the slide despite it not being fresh. |
| V7 | `cmd/guitartutor/live.go` `strumBuf` | Also mine, from the V1 work. Clearing the buffer at the end of *every* `onNotes` — including the not-waiting early return — dropped an anticipating player's strum whenever it arrived a batch or more before the wait engaged. | Replaced with an age-based prune at the arming floor, which only ever moves forward, so the buffer holds exactly the attacks that could still confirm and is bounded by `maxRecentStrums`. The buffer is also cleared on confirmation, so one attack cannot release two wait points. Tests: `TestDeadNoteWaitStrumBeforeTheWaitEngages`, `TestStrumBufferIsBounded`. |
| V8 | `internal/gpimport` `percussion` | **Introduced by the G1 fix.** Detecting drum kits by substring deleted every pitched instrument whose name merely contains the word: General MIDI's Steel Drums (115), Percussive Organ (18) and Melodic Tom, GPIF's own `pitchedPercussion` family, and refs like `perc-vibraphone`. Each vanished from the score with a warning claiming it was drums — the player opened a file and their part was simply gone. An all-"percussion" file became a hard error. | Every marker is matched exactly: the `drumKit` family value, a whole-name match against known kit names, a `drmkt` ref prefix, or MIDI channel 10. The two errors are not symmetric — an undetected kit imports as rests, which is visible and warned about; a pitched track misread as a kit disappears. Test: `TestPitchedInstrumentsAreNotPercussion`. |

## Known gaps, recorded rather than fixed

- For a chord mixing authored and inferred fingerings, the inferred note's
  fret is chosen without seeing the authored notes' frets, so it can sit
  outside the authored shape's span. It is always playable and never
  dropped — the property that matters — but a guitarist would finger it
  differently. Fixing it means teaching `internal/fretting.Assign` about
  pre-placed positions.
- MusicXML D.C./D.S./coda/fine jumps are detected and warned about, not
  followed. Their semantics compose in ways no bounded reading of the
  markup settles, and a wrong expansion teaches the wrong music.
- `midiimport.scale` divides by the file's PPQ, which would be a
  divide-by-zero on a division-0 header were it not for gomidi defaulting
  that to 960. It is load-bearing on a library default; no test can be
  written that fails against current code, so it is noted rather than
  guarded.
